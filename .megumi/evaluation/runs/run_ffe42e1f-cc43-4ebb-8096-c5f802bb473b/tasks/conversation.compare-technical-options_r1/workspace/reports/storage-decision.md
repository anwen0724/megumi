# 存储方案决策报告

> 本报告基于 `materials/` 下三份文档（`requirements.md`、`document-store.md`、`sqlite.md`）编写，材料未做任何修改。

## 约束与评价标准

依据 `materials/requirements.md`，项目的核心约束为：

| 编号 | 约束 | 原文依据 |
| --- | --- | --- |
| C1 | 离线优先 | requirements.md：「离线优先」 |
| C2 | 单机数据规模低于 2 GiB | requirements.md：「单机数据规模低于 2 GiB」 |
| C3 | TypeScript 团队维护 | requirements.md：「TypeScript 团队维护」 |
| C4 | 启动时间优先 | requirements.md：「启动时间优先」 |
| C5 | 必须支持事务 | requirements.md：「必须支持事务和全文检索」 |
| C6 | 必须支持全文检索 | requirements.md：「必须支持事务和全文检索」 |

评价标准据此确定为：

- **必选标准（硬性门槛）**：支持事务（C5）、支持全文检索（C6）、离线可用（C1）。
- **优选标准（加权比较）**：在低于 2 GiB 的单机规模下架构简单、维护成本低（C2、C3）；启动开销小（C4）；数据一致性风险可控。

## 方案对比

### 方案 A：文档存储（JSON 模型）

| 评价维度 | 事实（依据 `materials/document-store.md`） | 结论 |
| --- | --- | --- |
| 事务（C5） | 「复杂事务、关联查询和全文检索需要额外实现」 | **不满足**，事务需自行实现，无法满足硬性门槛 |
| 全文检索（C6） | 「复杂事务、关联查询和全文检索需要额外实现」 | **不满足**，全文检索需额外实现 |
| 离线优先（C1） | 文档存储本身可本地落盘，材料未提及服务依赖 | 基本满足 |
| 开发直观性（C3） | 「JSON 模型灵活、开发直观」 | 满足，对 TypeScript 团队友好 |
| 数据一致性 | 「数据一致性依赖应用层」 | 一致性风险由应用层承担，维护成本高 |

### 方案 B：SQLite

| 评价维度 | 事实（依据 `materials/sqlite.md`） | 结论 |
| --- | --- | --- |
| 事务（C5） | 「事务成熟」 | **满足** |
| 全文检索（C6） | 「支持 FTS5」 | **满足** |
| 离线优先（C1） | 「嵌入式、无需独立服务」 | **满足**，无需额外服务进程 |
| 单机规模（C2） | 嵌入式单机数据库，低于 2 GiB 规模完全适配 | 满足 |
| 启动时间（C4） | 嵌入式、无独立服务，启动无需连接外部进程 | 满足，有利于启动时间优先 |
| 维护成本（C3） | 「需要迁移管理和原生模块构建」 | 有额外成本，需通过工程化手段缓解 |

### 对比小结

- 方案 A 在「开发直观」上有优势，但**无法原生满足事务与全文检索两项硬性要求**，需要额外实现且一致性依赖应用层。
- 方案 B 原生满足全部硬性要求（事务、FTS5、离线嵌入式），仅在迁移管理与原生模块构建上有额外工程成本。

## 推荐结论

**推荐采用 SQLite 方案。**

理由（逐条对应材料事实）：

1. 只有 SQLite 同时满足「必须支持事务」（sqlite.md：「事务成熟」）与「必须支持全文检索」（sqlite.md：「支持 FTS5」）两项硬性门槛；文档存储方案这两项均「需要额外实现」（document-store.md），不满足必选标准。
2. SQLite 为嵌入式方案、「无需独立服务」（sqlite.md），契合「离线优先」约束（requirements.md），也避免引入额外进程带来的启动开销，符合「启动时间优先」（requirements.md）。
3. 数据规模低于 2 GiB 的单机场景（requirements.md）完全在 SQLite 的能力范围内，无需引入分布式或独立数据库服务。
4. 文档存储方案「数据一致性依赖应用层」（document-store.md），事务与检索缺口需要自研，长期维护成本高于 SQLite 所需的迁移管理成本。

## 风险与缓解

| 风险 | 材料依据 | 缓解措施 |
| --- | --- | --- |
| 原生模块构建复杂度 | sqlite.md：「需要原生模块构建」 | 使用预编译原生绑定（如 better-sqlite3 的预构建二进制）或纯 WASM 构建，将构建产物纳入 CI 固化；在 TypeScript 团队中封装统一的数据访问层，隔离原生细节 |
| 迁移管理负担 | sqlite.md：「需要迁移管理」 | 引入版本化迁移脚本与启动时迁移机制，与 TypeScript 代码一同维护并纳入测试 |
| 全文检索边界 | sqlite.md：「支持 FTS5」 | 提前验证 FTS5 分词与查询语法是否覆盖需求（如中文分词），必要时补充自定义分词器或辅助索引 |
| 若弃用 SQLite 而选文档存储 | document-store.md：「复杂事务、关联查询和全文检索需要额外实现」「数据一致性依赖应用层」 | 不推荐；仅在需求明确放宽事务/全文检索要求时，才考虑文档存储并自研一致性机制 |

## 结论

在「离线优先、低于 2 GiB、启动时间优先、必须支持事务与全文检索」的约束下，SQLite 是唯一原生满足全部硬性要求的方案；其迁移管理与原生模块构建风险可通过工程化手段缓解。因此最终推荐 **SQLite**。
