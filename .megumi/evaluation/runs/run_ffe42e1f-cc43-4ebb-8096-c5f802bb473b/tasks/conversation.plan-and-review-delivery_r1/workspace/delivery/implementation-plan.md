# 可恢复后台导入任务 — 实施计划

依据：`project/feature-brief.md`、`project/architecture.md`、`project/constraints.md`

## 目标

为本地桌面应用新增可恢复的后台导入任务：用户可发起导入、查看进度、取消任务，并在重启后继续查看最终结果。

## 分层职责（遵循现有架构）

| 层 | 职责 | 边界 |
|---|---|---|
| Renderer | 发起导入、轮询进度、点击取消、展示任务列表与结果 | 只调用 IPC Contract，不直接触碰业务状态 |
| IPC Contract | 定义 `start-import` / `get-task` / `list-tasks` / `cancel-task` 等通道及参数、返回结构 | 与渲染层唯一的通信面 |
| Main Host | 进程能力：任务执行、定时进度推送、取消中断、重启后恢复调度 | 不保存最终业务状态 |
| Product Owner | 保存并读取任务最终事实（状态、结果、错误），提供取消幂等处理 | 唯一最终业务状态来源 |
| Runtime Event | 只传递瞬时进度（如百分比、当前行数） | 永不落库、不作为最终状态 |
| 数据库 | 持久化任务事实，供重启后恢复与查询 | 最终事实的唯一存储 |

## 任务拆分（按依赖顺序）

### 阶段 A：数据与状态基础（无依赖，先行）

- **A1. 数据库表与仓储**
  - 说明：新增 `import_tasks` 表（id、类型、状态、总行数、完成行数、错误信息、最终结果、创建/更新时间）。状态机：`pending → running → succeeded | failed | canceled`。该表只保存任务最终事实：执行期间的瞬时进度（百分比、当前行数等）一律不写库，仅经 Runtime Event 传递；完成行数等数值只在任务到达终态时一次性写入。
  - 职责归属：Product Owner + 数据库。
  - 验证：单测覆盖表结构与持久化读写（含重启后数据仍在）；确认执行期间无进度写库路径。

- **A2. 任务状态机与取消幂等语义**
  - 说明：定义 `cancel` 处理规则——任务已是终态（succeeded/failed/canceled）时重复取消直接返回成功，不产生副作用；运行中取消标记为 canceled 并触发中断。
  - 职责归属：Product Owner。
  - 验证：单测覆盖状态机全量迁移（pending → running → succeeded | failed | canceled），以及“取消已终态任务”“取消运行中任务”“并发重复取消”三种场景。

### 阶段 B：主进程执行与事件（依赖 A1）

- **B1. 导入执行器（Main Host）**
  - 说明：执行导入逻辑，接收取消信号，周期性把瞬时进度通过 Runtime Event 发出；结束时只把最终事实写入 Product Owner。
  - 职责归属：Main Host（执行）、Product Owner（落最终状态）。
  - 验证：集成测试确认事件流只含瞬时进度、终态只来自数据库；取消信号能中断执行。

- **B2. 进度事件通道（Runtime Event）**
  - 说明：定义瞬时进度事件结构（taskId、percent、processedRows），仅供 UI 展示，无持久化路径。
  - 职责归属：Main Host → Renderer。
  - 验证：测试确认事件不含且不更新任何最终业务状态字段。

### 阶段 C：IPC 契约与界面（依赖 B1、B2）

- **C1. IPC Contract 实现**
  - 说明：实现 `start-import`、`get-task`、`list-tasks`、`cancel-task` 通道；Renderer 仅经由此层访问。
  - 职责归属：Main Host 与 Renderer 共同遵守契约。
  - 验证：契约测试确认请求/响应结构与文档一致；渲染层无直接状态访问。

- **C2. UI 交互**
  - 说明：发起导入按钮、进度展示（订阅 Runtime Event 刷新）、取消按钮、任务列表与重启后的结果展示。
  - 职责归属：Renderer。
  - 验证：手工/UI 测试覆盖发起、进度更新、取消、重启后查看结果。

### 阶段 D：恢复与容错（依赖 A1、B1）

- **D1. 启动恢复**
  - 说明：应用启动时由 Product Owner 读取未完成/已完成任务，恢复中断的 running 任务或将其标记为 failed（可配置策略），保证失败不阻止应用启动。
  - 职责归属：Main Host + Product Owner。
  - 验证：模拟崩溃后重启，应用正常启动且任务状态符合预期。

- **D2. 端到端验收**
  - 说明：按 feature-brief 场景走完整链路：发起 → 进度 → 取消 → 重启 → 查看结果。
  - 职责归属：全部模块联调。
  - 验证：端到端测试通过；确认 Runtime Event 未成为任何最终状态；取消幂等；启动不被失败阻断；无云同步；本阶段不涉及打包验证。

## 依赖关系图

```
A1 ──┬──> B1 ──> C1 ──> C2
A2 ──┘   │
         └──> D1 ──> D2
```

- A1、A2 无前置依赖，可并行。
- B1 依赖 A1（执行落库）与 A2（取消依赖幂等语义）；B2 仅定义事件结构、无数据依赖，但事件由执行器发出，其集成验证依赖 B1。
- C1 依赖 B1、B2；C2 依赖 C1。
- D1 依赖 A1（直接读取任务事实）与 B1（恢复调度，经 B1 传递 A1/A2 依赖）；D2 为最终联调。

## 每项任务的验证方式

| 任务 | 验证方式 |
|---|---|
| A1 | 单元测试（状态迁移、持久化、重启后数据仍在） |
| A2 | 单元测试（终态重复取消、运行中取消、并发取消） |
| B1 | 集成测试（事件仅瞬时进度、终态仅来自数据库、取消可中断） |
| B2 | 集成测试（事件不写最终状态） |
| C1 | 契约测试（通道与结构一致、渲染层无直接访问） |
| C2 | UI 测试（发起/进度/取消/重启后查看） |
| D1 | 崩溃恢复测试（重启正常启动、任务状态正确） |
| D2 | 端到端验收（完整场景通过） |
